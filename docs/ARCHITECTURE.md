# Архитектура

Документ описывает то, что есть в коде на дату 2026-10-17. Числа по умолчанию взяты из `app/config.py`, `app/rules_default.json` и `app/detector_rules.py`. Что измерено, а что нет, см. [QUALITY.md](QUALITY.md).

## Компоненты

| Файл | Роль |
|---|---|
| `app/asgi.py` | Точка входа ASGI (`app.asgi:app`). Отказывает в старте при `SYNTHETIC_DETECTOR` без `ALLOW_SYNTHETIC_DETECTOR=1` |
| `app/main.py` | HTTP-слой (FastAPI), `_Guard` (ASGI-middleware: ключ, потолок байт, таймауты), эндпоинты |
| `app/config.py` | `Settings` из переменных окружения и проверка инвариантов (бюджет `< 300 с`, `UPLOAD + BUDGET < 300`) |
| `app/jobs.py` | `JobStore`: очередь, admission, дочерние процессы, watchdog, журнал статусов на диске |
| `app/worker.py` | Точка входа дочернего процесса (`python -m app.worker in out`), строгий валидатор результата, маппинг кодов ошибок |
| `app/pipeline.py` | Два этапа анализа, наблюдения, зона оператора, гейты покрытия, вердикт |
| `app/detector.py` | YOLOX через ONNX Runtime: letterbox, декодирование, NMS, проверка SHA-256 |
| `app/detector_rules.py` | Загрузка и проверка набора правил, статус `validated` |
| `app/rules_default.json` | Правила по умолчанию (все кандидаты, отключены) |
| `app/norms.py` | Кандидатные нормативные ссылки для описаний (не обоснование вывода) |

## Конвейер анализа

### Этап 1: выборка и наблюдения

- Декодирование видео через OpenCV, выборка **4 кадра/с** (`SAMPLE_FPS`, по умолчанию 4), ширина кадра для детектора **640 px** (`stage1_width`).
- Детекция людей: YOLOX-S, класс `person` (индекс 0). Вход 640x640 с letterbox (заполнение 114, BGR, без нормировки), NMS 0.45, порог уверенности `DETECTOR_CONF` (0.30). Декодирование совпадает с официальным `demo_postprocess` и `multiclass_nms`, это проверено при обзоре.
- Сетка движения: кадр уменьшается до **48x27** клеток, порог пикселя 25. Из неё и из боксов людей строится карта активности.
- **Адаптивная зона оператора:** по тепловой карте (сетка 24, паддинг 0.25) оценивается область, где стоит оператор. Если зона ненадёжна (заполненность ниже `min_occupancy_to_analyse`, жёсткий пол 0.15), задание завершается `zone_unreliable`. Оператор вручную задаётся через `OPERATOR_ZONE=x0,y0,x1,y1` (нормализованные координаты) или поле `zone.override` в правилах. Полная доверенность зоны — при заполненности от 0.6.
- Гейт покрытия по людям: доля кадров с людьми ниже `min_person_sample_ratio` (жёсткий пол 0.10) даёт `too_few_detections`.

Этап 1 формирует **наблюдения** (например, два человека в зоне оператора). Наблюдения всегда считаются и попадают в локальный экспорт для ручной проверки. Они не влияют на вердикт напрямую.

### Этап 2: уточнение

- Выборка **8 кадров/с** (`stage2_fps` = 8.0) вокруг границ кандидатов с полями по 3 с (`stage2_margin_sec`).
- Суммарно не более **60 с** видео (`stage2_max_total_sec`).
- Резерв на финализацию 20 с (`deadline_reserve_sec`). Если времени мало, окна этапа 2 сокращаются или пропускаются полностью. Пропуск помечается `truncated=True` в `meta` (не в публичном ответе). Вердикт из одного этапа 1 при этом выдаётся с понижающим множителем 0.8 и `refined=False`.
- Проверка дедлайна выполняется на каждом кадре этапов 1 и 2 и на кадрах доказательств.

### Наблюдения, правила, вердикт

Цепочка принятия решения (`app/pipeline.py`, `app/detector_rules.py:states`):

1. **Наблюдения** (`observations`) — всегда. Тип, интервал, уверенность. Идут только в локальный экспорт (`local_private/observations/`), публично не отдаются.
2. **Правило активно**, если `enabled` **и** допустимо для вердикта (`verdict_eligible`) **и** (`validated` **или** `ALLOW_UNVALIDATED_RULES=1`).
3. **Вердикт `violation`** выдаётся только при срабатывании активного правила. Иначе — `no_violation`.
4. **Нет ни одного активного правила** → `failed/no_validated_rule`. Это единственный путь без валидированного правила, и он не выдаёт `no_violation` и не выдаёт `violation`.

Формат записи holdout для валидированного правила (`app/detector_rules.py:holdout_ok`):
`{"n_clips": int 5..10000, "precision": (0,1], "recall": (0,1], "evaluated_at": "YYYY-MM-DD" (строгий ISO, не в будущем), "split_id": str, "tool": "tools/evaluate.py"}`.
Схема правил закрыта: неизвестные ключи дают `invalid_config`. Запись — это декларация, скопированная из вывода `tools/evaluate.py` и проверенная человеком. Она не привязана криптографически к конкретному запуску. Это известное принятое ограничение: проверка — гейт правдоподобия, а не доказательство.

Ограничения, зашитые в код:

- Правило `second_person_in_operator_zone` **не может** дать нарушение: оно исключено из вердикта (`NEVER_VERDICT`, `observation_only`). Дополнительно это проверяет мутационный тест.
- Правило считается валидированным только при полной записи `holdout` (`holdout_ok`): `n_clips` не меньше 5, `precision` и `recall` конечные числа в [0, 1], `evaluated_at` — корректная дата ISO, `split_id` непустой, `tool` равен `tools/evaluate.py`. Статус `status: "validated"` без записи holdout отвергается как `invalid_config`.
- Неизвестные ключи правил отвергаются (`detector_rules.py:62-63`). Нижние пороги гейтов (0.10 и 0.15) заданы в коде и не переопределяются JSON.
- Все правила в `app/rules_default.json` имеют `enabled: false` и `status: "candidate"`.

Коды `failed` от пайплайна и воркера перечислены в [README.md](../README.md#api-контракт) (раздел «API (контракт)», таблица кодов).

## Очередь и изоляция воркеров

Цель: ни одно задание не превышает 5 минут от загрузки до статуса, и сбой одного задания не влияет на сервис.

- **Дочерний процесс на задание.** `start_new_session=True`, отдельная группа процессов. Поток родителя ждёт завершения. Stdio дочернего процесса перенаправлен в `DEVNULL`, логи не содержат stderr или трассировок.
- **Бюджет от постановки в очередь.** `submitted_at` берётся в начале запроса (`_Guard`, `scope.state.t0`), дедлайн = `submitted_at + JOB_BUDGET_SEC` (230 с). Время ожидания в очереди входит в бюджет.
- **SIGKILL группы процессов** при достижении дедлайна (`os.killpg(..., SIGKILL)`, запасной `proc.kill()`).
- **Watchdog.** Если родитель не завершил задание через `KILL_GRACE_SEC` (2 с) после дедлайна, задание принудительно переводится в `failed`, процесс убивается. Финальный статус записывается один раз (`_finish`).
- **Дочерний процесс следит за родителем** (`JOB_PARENT_PID`, `_watch_parent`): при гибели родителя выходит в пределах нескольких секунд.
- **Admission control.** Ёмкость = `WORKERS + QUEUE_LIMIT` (2 + 20 по умолчанию). Сверх ёмкости — 429. Задание также отклоняется, если прогнозируемое завершение превышает `JOB_BUDGET_SEC + ADMISSION_MARGIN_SEC`. Оценка времени = максимум из последних 20 завершённых (не по таймауту) заданий, холодный старт 60 с (`JOB_ESTIMATE_SEC`). Занятый слот, который работает дольше оценки, считается занятым до собственного дедлайна.
- **Статус на диске.** Каждое задание пишет `DATA_DIR/<job_id>.json` (`processing`, затем `done` или `failed`). Ответ `GET` при отсутствии записи в памяти читается с диска и повторно валидируется. Записи истекают через `JOB_TTL_SEC` (7200 с).
- **Очистка.** Удаляются только файлы, имена которых совпадают с шаблонами `_TEMP_RE` / `_RESULT_RE` (32 hex). Осиротевшие загрузки старше `ORPHAN_MAX_AGE_MIN` (10 мин) удаляются при старте и периодически.
- **Валидатор результата** (`worker.validate_result`): вердикт из набора `violation` / `no_violation`; `no_violation` ⇔ пустой список; `violation` ⇔ 1..50 нарушений; у каждого нарушения 1..3 кадра доказательств; `timecode_sec` и `timestamp_sec` — конечные числа ≥ 0; JPEG: base64 строгий, маркеры `FFD8…FFD9`, 101 байт — 2 МБ, `cv2.imdecode` даёт ненулевой размер 16–4096 px. Публичная проекция содержит только разрешённые поля. Проверка выполняется в дочернем процессе, при чтении результата родителем и при чтении с диска.
- **Коды ошибок** только из закрытого списка (`ALLOWED_ERROR_CODES`). Любое другое исключение превращается в `analysis_failed`. Ошибка без валидного кода не сохраняет текст исключения.

Известные ограничения очереди (см. также раздел «Известные ограничения» в [QUALITY.md](QUALITY.md)):

- В режиме `analyze_fn` (встроенный, только для тестов) задание нельзя убить. Это задокументировано.
- Лимит памяти `WORKER_MEM_MB` (RLIMIT_AS) работает только на Linux. На macOS он не действует, остаётся только дедлайн.
- Лимит CPU (`RLIMIT_CPU`) **удалён** намеренно: CPU-секунды суммируются по потокам ONNX Runtime и убивали бы корректные задания раньше дедлайна (`app/worker.py`, комментарий у строки 283).

## ASGI-защита (`_Guard`)

Выполняется до FastAPI и парсинга multipart:

1. Ключ `X-API-Key` сравнивается из заголовков scope **до** чтения тела. Неверный ключ → 401 без чтения байт тела.
2. `Content-Length` больше лимита (`MAX_UPLOAD_MB` + 1 МиБ запаса на кадрирование) → 413 до чтения тела.
3. При потоковой передаче счётчик байт прерывает приём с 413 (примерно cap + один чанк).
4. Пауза между чанками больше `RECEIVE_TIMEOUT_SEC` (15 с) или общее время приёма больше `UPLOAD_TIMEOUT_SEC` (60 с) → 408.
5. Проверка `X-API-Key` повторяется в FastAPI-зависимости `auth` (второй рубеж). Оба источника читают один и тот же ключ.

Ограничения: тайм-ауты приёма тела и лимит байт действуют на путь `POST /api/v1/analyze`. Для других путей и методов тело читается uvicorn без таймаута (замечание L1 в `REVIEW_CRITICAL.md`, статус не перепроверен). Медленные заголовки на уровне uvicorn вне области `_Guard`. Редирект 307 отражает заголовок `Host` (L1).

### Заголовки и лимиты (этап 6)

`_Guard` (`app/main.py`) добавляет три части. (1) На всех ответах `/api/*`, включая ранние ответы `_Guard` и обработчики 422/500, стоят `Cache-Control: no-store`, `Pragma: no-cache`, `X-Content-Type-Options: nosniff`. `/healthz` и `/static` их не получают. (2) Лимиты частоты в памяти процесса: `MAX_INFLIGHT_UPLOADS` (4 одновременные загрузки), `RATE_LIMIT_PER_MIN` (30 загрузок в минуту на IP), `POLL_LIMIT_PER_MIN` (600 опросов в минуту на IP; проверка до ключа). Адрес для лимитов берётся из сокета (`scope["client"]`). `X-Forwarded-For` учитывается только при `TRUST_PROXY=1`. Чтобы uvicorn не подменял адрес сам, его запускают с `--no-proxy-headers`. (3) `/docs`, `/redoc` и `/openapi.json` отключены. Тесты: `tests/test_hardening.py` (38 тестов). Граница доступа к заданиям описана в README и [DEPLOY.md](DEPLOY.md).

## Приватность

- В логах только `job_id`, статус, код возврата, время работы, имя класса исключения или errno. Имена файлов, пути и текст сцен не логируются.
- Публичные ошибки — статические коды из закрытого списка. Тела ошибок HTTP статические.
- Stdout и stderr дочерних процессов — `DEVNULL`.
- Наблюдения, метаданные и кадры вне публичного ответа не передаются. Публичный ответ содержит только поля `job_id`, `status`, `verdict`, `violations` (и `error` при ошибке).
- `local_private/` (инвентаризация, метки, сплиты, предсказания, наблюдения) и `data/`, `weights/`, `*.mov`, `*.mp4` добавлены в `.gitignore`. Сборка `.gitignore` чувствительна к регистру (см. L10).
- Инструменты (`inventory`, `import_labels`, `annotate`, `run_local`, `evaluate`) печатают только счётчики и числа. Инвентаризация использует allow-list расширений и изолированный probe, `annotate` слушает только `127.0.0.1` и проверяет `Host` и `client`.
- Распознавание лиц не выполняется. Кадры доказательств содержат нарисованную зону и боксы. Допустимость необработанных лиц в публичных кадрах доказательств — вопрос политики, код его не решает.

## Инструменты этапа 2 (train-only)

`tools/train_probe.py` — пробный анализ признаков на train-части. Холдаут проверяется до открытия файла: sha16 должен быть в train, индекс не должен быть заявлен никакой не-train записью. Извлечение выполняется по одному клипу в дочернем процессе. Задание передаётся одной JSON-строкой через stdin, stderr в `DEVNULL`, SIGKILL по `--budget-sec`. В кэш пишутся только числовые временные ряды (боксы, классы, сетка движения, без изображений). Выбор конфигураций: вложенный LOO по клипам (единица — один sha16). Нулевое распределение: перестановки меток с той же процедурой выбора. Метрики считаются тем же оценщиком, что и `tools/evaluate.py`. Stdout и `summary.json` содержат только агрегаты. Правило приватности S1: **пути к медиафайлам не передаются в argv нигде** (ни в `train_probe`, ни в `inventory`, ни в `run_local`). Путь и задание идут через stdin, `ps` их не показывает. `tools/annotate_attrs.py` — слепая разметка атрибутов моментов: только train, подсказки с тегами (label / control) скрыты от интерфейса, ответы пишутся как `attr`-записи, сводка — только счётчики.

## Исследовательские инструменты этапа 3 (не в продакшне)

`tools/feature_models.py` — локальный пилот VLM (Qwen2-VL-2B, 4-bit MLX), работает только в `.venv-research`. Задание передаётся в дочерний процесс через stdin, stderr в `DEVNULL`. Лимит памяти (по умолчанию `PILOT_MEM_MB` = 8192) enforced родительским watchdog: heartbeat из ребёнка и опрос RSS, при превышении SIGKILL всей группы и статус `memory_cap`. Сырой текст модели остаётся в памяти ребёнка и сразу сводится к enum-коду (или -1). В кэш пишутся только числовые коды, печатаются только агрегаты. Пилот не подаёт псевдоразметку в `train_probe`.

`tools/annotate_audit.py` — минимальный слепой аудит C02: 10 моментов (5 меток + 5 контрольных; контроль a — тот же клип, парный; b и c — другой клип, непарные) × q1/q3/q7, T1 и V1; роль R1 по квадрантам для 17 train-клипов. Идентификаторы стабильны (хеш от sha, t и pid), ответы привязываются по (sha, t) и не переписываются. Теги label/control не покидают сервер. Состояние на 2026-10-18: аудит завершён, 67 из 67 ответов. Сводка `audit_summary` (`progress`, `r1`, `pairing`) — только счётчики. R1 использует грубый квадрантный запасной вариант: экспорт наблюдений не содержит поля зоны оператора.

## Исследовательские инструменты этапа 5 (train-only, не в продакшне)

`tools/stage5_encoder.py` — ONNX-энкодер SigLIP2. Файл `vision.onnx` закреплён по sha256 (проверка хеша); экспорт выполняется только при отсутствии файла. `tools/stage5_model.py` — признаки, L2-логистическая модель, полностью вложенная clip-LOO с внутренним отбором по J = F1 + hit. `tools/stage5_probe.py` — оркестрация протокола: перестановки, базовые уровни, метрики, сводка. Самопроверка — `tools/stage5_selftest.py`. Инструменты только локальные; правила не включаются, продакшн-конвейер не меняется.

Дочерние процессы получают задание через stdin, stderr направлен в `DEVNULL`, назад возвращается только числовой JSON. Память дочернего процесса контролирует родительский сторож: при превышении лимита процесс-группа завершается, статус `memory_cap`, остатков нет (проверено тестом с лимитом 256 МБ). Один глобальный сторож на 90 минут учитывает остаток времени: фазы останавливаются со статусом `incomplete`, а n_perm по результатам не меняется. Декодирование fail-closed: ожидаемое число кадров вычисляется из длительности; при несовпадении статус `decode_incomplete`, кэш не пишется, единица считается сбоем, GO запрещён.

Результат прогона и ограничения: [QUALITY.md](QUALITY.md), раздел 3e.

## Исследовательские инструменты этапа 7 (train-only, не в продакшне)

`tools/stage7_core.py` (326 строк) — ядро: признаки внутри клипа, медианное центрирование по клипу (без меток), направление с робастной диагональной шкалой и единичной нормой, вложенная clip-LOO 17 × 16, метрики. Разбиение строго по клипам: клип, по которому выбирается шкала, направление или порог, не входит в множество, на котором он оценивается (core.py:78-84, 100-106, 164-181, 201-231). Нулевое распределение N1 (position-matched transplant) использует опорный пул из 13 значений: 12 негативов и наблюдаемое u_k каждого позитива (core.py:225-227, исправление S7-1). Циклических сдвигов (roll, circular, cyclic) в коде нет. `tools/stage7_wcr.py` (298 строк) — оркестрация протокола по двум семьям, базовые уровни (always-positive, duration-only, random-time), сводка только агрегатами. Дочерний процесс считается под сторожем памяти: при превышении лимита процесс-группа завершается со статусом `memory_cap`. Диагностики signed ρ и ρ по негативам только выводятся и не входят ни в один критерий. `tools/stage7_selftest.py` (292 строки) — синтетическая самопроверка 10/10: `python -m tools.stage7_selftest DIR --n-perm 200 --power-reps 5`. Инструменты не импортируются из `app/` и не меняют правила или вердикт. Протокол: [PROTOCOL_STAGE7.md](PROTOCOL_STAGE7.md). Результат и ограничения: [QUALITY.md](QUALITY.md), раздел 3f.

## Инструменты этапа 8 (локальная разметка интервалов и гейт, не в продакшне)

`tools/annotate_intervals.py` (499 строк) и `tools/annotate_intervals_ui.py` (143 строки) — отдельное минимальное приложение разметки интервалов, слушает только 127.0.0.1. Маршруты ограничены обучающим набором через allowlist по task id; маршруты `annotate` (импорт, разбиение, все клипы, атрибуты) не подключаются. Запись идёт в журнал ревизий с проверкой ревизии (409 при устаревшей). `tools/_selftest_intervals.py` (424 строки) — самопроверка 96/96, включая браузерные проверки. `tools/stage8_audit.py` (277 строк) — гейт достаточности, только агрегаты: `--print-lock` не читает данные; `--gate-only --expect-lock <digest>` проверяет sha снимка меток и фиксацию протокола, не открывает клипы и не читает кэши, хеширует 8 неизменяемых артефактов до и после запуска, записывает итог один раз (режим 0400) и отказывает (код 2) при неверной фиксации, неверном sha снимка или уже существующем итоге. Самопроверка: `tools/stage8_selftest.py` (218 строк). Продакшн остаётся fail-closed. Протокол: [PROTOCOL_STAGE8.md](PROTOCOL_STAGE8.md). Результат и ограничения: [QUALITY.md](QUALITY.md), раздел 3g.

## Инструменты этапа 10 (exploratory weakly-supervised fit, research-only, не в продакшне)

`tools/stage10_*` — исследовательские инструменты предрегистрированного exploratory fit на train: слабые позитивы из 2 подтверждённых интервалов и 12 провайдерских негативных клипов. Тот же паттерн изоляции и отказа, что у этапов 8 и 9: только train, отказ при обращении к holdout, агрегатные выводы, один запуск (по замыслу; протокол зафиксирован lock, запуск выполнен однократно: `STOP_NOT_EVALUABLE`, обучения не было). Веса не сохранялись (`model_artefact_saved=false`) и не поставляются. Продакшн остаётся fail-closed. Дизайн и результат: [QUALITY.md](QUALITY.md), раздел 3i.
