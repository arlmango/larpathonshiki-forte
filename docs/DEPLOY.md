# Развёртывание (офлайн, без публикации и покупок)

Цель: поднять сервис на одной машине внутри сети организатора, без публикации в интернете, без платных ресурсов и без внешних сервисов во время работы. Сеть нужна только один раз, для `tools/fetch_weights.py`, если веса не скопированы заранее.

Перед развёртыванием прочитайте главный вывод в [README.md](../README.md): без валидированных правил сервис возвращает `failed/no_validated_rule` и **не выносит вердикты**. Развёртывание для демонстрации ≠ готовность к продукту.

## 1. Что переносится на машину

- Репозиторий целиком (`app/`, `tools/`, `static/`, `docs/`, `requirements.txt`).
- Каталог `weights/` с файлами `yolox_s.onnx` (минимум; `yolox_tiny.onnx` и `yolox_nano.onnx` — по выбору). Файлы проверяются по SHA-256 при загрузке модели (`app/detector.py`). Хеш yolox_s: `c5c2d13e59ae…`.
- Окружение Python 3.13. Два варианта:
  - скопировать готовый `.venv` (нужна та же ОС и архитектура);
  - установить из `requirements.txt` на целевой машине. **Офлайн-установка из колёс не проверялась.** Для неё заранее соберите колёса (`pip download -r requirements.txt -d wheels/`) на машине с сетью и установите с `--no-index --find-links wheels/`. Эти команды не запускались.
- **Не переносить** `local_private/`, `data/`, `.env`-файлы с ключами и содержимое каталогов с видео. В `local_private/` лежат метки и карта инвентаризации. Они остаются на машине оператора.

Проверка целостности весов перед стартом:

```bash
shasum -a 256 weights/yolox_s.onnx    # должно совпасть с c5c2d13e59ae883e6af3b45daea64af4833a4951c92d116ec270d9ddbe998063
```

## 2. Запуск

```bash
cd <корень репозитория>
export API_KEY='<длинный случайный секрет>'      # обязателен, иначе приложение не стартует
export WORKERS=2                                   # параллельные воркеры заданий
export JOB_BUDGET_SEC=230                          # по умолчанию; проверка: UPLOAD_TIMEOUT_SEC + JOB_BUDGET_SEC < 300
export UPLOAD_TIMEOUT_SEC=60
export REQUIRE_EMPTY_DATA_DIR=1                    # рекомендуется: отказ от старта при непустом DATA_DIR
export DATA_DIR=<абсолютный путь к пустому каталогу>   # свежий пустой каталог на каждый запуск
# НЕ задавать на продукции:
#   ALLOW_UNVALIDATED_RULES, SYNTHETIC_DETECTOR, ALLOW_SYNTHETIC_DETECTOR, TRUST_PROXY
uvicorn app.asgi:app --host 0.0.0.0 --port 8000 --workers 1 --no-proxy-headers
```

За туннелем или прокси на loopback используйте `--host 127.0.0.1` и тот же набор флагов. Подробности — в разделе 2a.

- **Один процесс uvicorn** (`--workers 1`). Параллельность заданий задаёт `WORKERS` (число дочерних процессов-воркеров). Очередь и статусы хранятся в `DATA_DIR` (по умолчанию `data/jobs` в корне проекта). Работа нескольких процессов uvicorn не проверялась: по рассуждению, статус должен читаться через диск, но это не измерено.
- `--host 0.0.0.0` открывает сервис во всех интерфейсах. Используйте его **только** за сетевым экраном организатора (см. раздел 3).
- Запускайте из корня проекта. Пути по умолчанию привязаны к корню, но проверяйте логи старта.
- Тест на доступность без ключа: `curl -s http://127.0.0.1:8000/healthz` → `{"ok":true}`.

Остановка: `SIGTERM` процессу uvicorn. Приложение переводит незавершённые задания в `failed/service_shutting_down` и удаляет временные файлы (проверено при обзоре). Жёсткий `SIGKILL` родителя оставляет задание в `processing`, дочерний процесс выходит в течение нескольких секунд, а задание в итоге становится `job_lost` (проверено при обзоре).

## 2a. Параметры защиты API

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `MAX_INFLIGHT_UPLOADS` | 4 | Одновременные загрузки; сверх них 429 |
| `RATE_LIMIT_PER_MIN` | 30 | Загрузки в минуту на IP; сверх них 429 |
| `POLL_LIMIT_PER_MIN` | 600 | Опросы `GET /api/v1/jobs/*` в минуту на IP; сверх них 429 |
| `BIND_JOBS_TO_KEY` | `1` | Задание привязано к хешу ключа (в памяти). `0` отключает |
| `REQUIRE_EMPTY_DATA_DIR` | не задана | `1`: сервис не стартует, если `DATA_DIR` непуст. Файлы не удаляются |
| `TRUST_PROXY` | не задана | `1` доверяет первому `X-Forwarded-For`. Не включать без отдельного решения по безопасности |

- Заголовки на всех ответах `/api/*`: `Cache-Control: no-store`, `Pragma: no-cache`, `X-Content-Type-Options: nosniff`. Это касается и ранних ответов 401, 400, 408, 413, 415, 429, а также 422 и 500. `/healthz` этих заголовков не получает.
- `/docs`, `/redoc` и `/openapi.json` отключены (404).
- Лимиты работают в памяти одного процесса. Поэтому uvicorn запускается с `--workers 1`. Параллельность заданий задаёт `WORKERS`.
- **Запуск за туннелем или прокси на loopback: `--no-proxy-headers` обязателен.** По умолчанию uvicorn доверяет `X-Forwarded-For` от `127.0.0.1` и `::1` и подменяет адрес клиента. Тогда подмена заголовка обходит лимиты. С флагом все клиенты туннеля делят один bucket. Это ограничение, а не обход.
- `TRUST_PROXY=1` доверяет первому `X-Forwarded-For`. Клиент может подделать этот заголовок, если прокси его не перезаписывает. Без отдельного решения по безопасности не включать.
- `REQUIRE_EMPTY_DATA_DIR=1` только проверяет и отказывает в старте. Удаления файлов в коде нет. Используйте пустой каталог на каждый запуск, а старые записи переносите вручную.

## 3. Сеть и доступ

- Ключ `X-API-Key` обязателен для всех эндпоинтов, кроме `/healthz` и статической страницы `/`. Сравнение ключа — через `hmac.compare_digest`.
- Ключ передавайте только по доверенному каналу и не записывайте его в репозиторий, логи и историю команд. Смените его после демонстрации.
- Открывайте порт только внутри сети организатора. Для локальной работы используйте `--host 127.0.0.1`.
- Сервис не обращается в интернет во время работы. Единственный сетевой код — `tools/fetch_weights.py` (urllib), вызывается вручную.
- Не публикуйте сервис в интернет без отдельного решения по безопасности. Ограничение частоты неверных ключей в коде не реализовано: при неверном ключе POST отвечает 401 до лимита загрузок.
- **Граница доступа к заданиям.** Ключ один и общий, поэтому любой держатель `API_KEY` читает любое задание. Привязка `BIND_JOBS_TO_KEY=1` сравнивает хеш ключа с тем, кто отправил задание. Это не разделение пользователей. Привязка хранится в памяти процесса: после перезапуска её нет, и задание читается любым ключом. Ключ по замыслу общий; разделение людей требует отдельного решения.

Известные ограничения сети (см. [ARCHITECTURE.md](ARCHITECTURE.md#известные-ограничения)):
- Тайм-ауты приёма тела и лимит байт действуют на `POST /api/v1/analyze`. Другие пути читаются uvicorn без таймаута. Лимит частоты действует и на `GET /api/v1/jobs/*`.
- Медленные заголовки (slow-loris) на уровне uvicorn не ограничиваются приложением.

## 4. Проверка работоспособности

| Проверка | Команда | Ожидаемо |
|---|---|---|
| Жив ли процесс | `GET /healthz` | 200 `{"ok": true}` |
| Модель и правила | `GET /api/v1/model` с `X-API-Key` | `model.available: true`, `model.validated`, `model.allow_unvalidated_rules` (должно быть `false`), `model.rules[]` со статусами `candidate` |
| Очередь | то же ответ, поле `queue` | счётчики `records`, `estimate_sec` |
| Неверный ключ | `POST /api/v1/analyze` без ключа | 401 без чтения тела |
| Заголовки защиты | `GET /api/v1/model` с ключом, смотреть заголовки ответа | `Cache-Control: no-store`, `Pragma: no-cache`, `X-Content-Type-Options: nosniff` |
| Документация отключена | `GET /docs` | 404 |
| Прокси-заголовки отключены | запуск с `--no-proxy-headers` (см. раздел 2a) | флаг присутствует в строке запуска |

Ожидание для текущей версии без валидированных правил: задание проходит пайплайн и завершается `failed` с `error: "no_validated_rule"`. Это **правильное** поведение. Если `ALLOW_UNVALIDATED_RULES` не задан, статус `done` без валидированного правила означает нарушение fail-closed: такой результат нужно считать ошибкой и сообщить разработчику.

Если `model.allow_unvalidated_rules` равно `true`, сервис работает в демонстрационном режиме. Такой режим нельзя выдавать как результат проверки.

## 5. Бюджет времени: 5 минут

Требование: от загрузки до конечного статуса — меньше 5 минут.

- Приём загрузки: до `UPLOAD_TIMEOUT_SEC` = 60 с (общий таймаут), пауза между чанками не больше `RECEIVE_TIMEOUT_SEC` = 15 с.
- Бюджет задания: `JOB_BUDGET_SEC` = 230 с, **от момента постановки в очередь**. Время ожидания в очереди входит в бюджет.
- Худший случай: 60 + 230 = **290 с** < 300 с. Проверка стоит в `app/config.py`: сервис не стартует, если сумма ≥ 300.
- Поздний SIGKILL: watchdog срабатывает через `KILL_GRACE_SEC` (2 с) после дедлайна. Итоговый статус не превышает бюджет более чем на несколько секунд.

Важно:
- Время, за которое клип пройдёт пайплайн, **не измерено на реальных клипах** (см. [QUALITY.md](QUALITY.md)). На синтетике 145 с 1080p занимало 78 с под нагрузкой.
- Нагрузка: ONNX Runtime использует `DETECTOR_THREADS` (по умолчанию 4) на задание, поэтому два параллельных воркера мешают друг другу. Замер координатора: этап 1 для клипа 145 с 1080p занял 131 с под нагрузкой против 66 с на тихой машине.
- Рекомендация для демонстрации: `WORKERS=1` или `DETECTOR_THREADS=2`, либо `DETECTOR_MODEL=yolox_tiny`, либо `SAMPLE_FPS=3`. Перед демонстрацией один прогон засечь на тихой машине. Замер при `WORKERS=2` на реальных клипах не проводился.
- Admission control (429) отклоняет задания, которые не успели бы в бюджет. Клиенту нужен повтор.

## 6. Что делать после демонстрации

- Удалить `data/jobs/` (после истечения `JOB_TTL_SEC` записи исчезают сами).
- Сменить `API_KEY`.
- Оставить `local_private/` на машине оператора, не публиковать его.
- Для продуктового использования: выполнить процедуру валидации из [QUALITY.md](QUALITY.md), подтвердить применимость норм пользователем и только после этого включать правила.
