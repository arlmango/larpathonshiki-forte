Короткая инструкция для проверяющих. Все числа ниже взяты из журнала проекта (`docs/COORDINATION.md`), `README.md`, `docs/QUALITY.md`, `docs/ARCHITECTURE.md`, `docs/DEPLOY.md`, `docs/LICENSES.md`. Где что-то не измерено, это написано явно.

## 1. Что это и честный статус

Локальный сервис: принимает видеоклип по HTTP, прогоняет его через детектор людей YOLOX-S (ONNX Runtime, CPU) и правила, возвращает результат задания.

**Статус одной строкой:** production работает в режиме fail-closed. Без валидированных правил задание завершается `failed` с кодом `no_validated_rule`, вердикт `violation` или `no_violation` не выдаётся. Работающий локальный инференс не означает работающий детектор нарушений: качество обнаружения нарушений на реальных данных не измерено, ни одно правило не валидировано.

Ещё две вещи для проверяющих. **План хостинга** в [RELEASE_PLAN.md](RELEASE_PLAN.md) — только план и проверка готовности. Он не выполнен: публикации, постоянных ключей и покупок не было. Проверка готовности релиза (`tools/release_check.py`) даёт **NOT READY** только потому, что git-репозиторий пуст и место хостинга не выбрано. Итог: 0 блокирующих, 0 ручных, 35 задокументированных известных исключений (`KNOWN_OK`, по записи на файл и sha16). Минимальный вариант публикации (что видно наружу, провайдер, срок жизни, действия пользователя) описан в `docs/RELEASE_PLAN.md` в разделе «НА СОГЛАСОВАНИЕ». Он **не согласован**, ничего не опубликовано.

**Демо-видео.** Файл `local_private/demo/forte_demo.mp4` существует и проверен координатором: 128 с, 1280×720 при 30 fps, кодек avc1, 1.36 МБ, воспроизводится, строк ключей нет. Это пояснительный синтетический клип с подписями, а не запись приложения. В нём есть **реальный локальный smoke** через API: продакшн-режим даёт `failed/no_validated_rule`, демонстрационный путь помечен «НЕ валидировано». Клип создан `tools/demo_video.py` в исследовательском окружении. Файл в `.gitignore`; его нужно приложить к сдаче отдельно.

## 2. Воспроизводимый запуск

Проверено: Apple M5, 16 ГБ, macOS, Python 3.13 (`.venv`).

### 2.1. Окружение и веса

```bash
cd <корень репозитория>
uv venv .venv
uv pip install --python .venv/bin/python -r requirements.txt
.venv/bin/python -m tools.fetch_weights            # по умолчанию yolox_s; нужна сеть один раз
```

- `requirements.txt`: fastapi, uvicorn[standard], python-multipart, opencv-python-headless, numpy, onnxruntime, certifi, openpyxl (версии закреплены, кроме uvicorn[standard], python-multipart и numpy).
- `tools.fetch_weights` принимает `yolox_s` (по умолчанию), `yolox_tiny`, `yolox_nano`, `all`, флаг `--force`. Каждый файл проверяется по SHA-256 из `app/detector.py`; при несовпадении файл не сохраняется, код возврата не 0.
- Офлайн-установка из колёс не проверялась. Установка через `uv` на чистой машине не проверялась: окружение проекта собрано ранее и использовалось повторно.

### 2.2. Запуск сервиса

```bash
export API_KEY='<длинный случайный секрет>'        # обязателен, иначе приложение не стартует
export REQUIRE_EMPTY_DATA_DIR=1                    # рекомендуется: отказ от старта при непустом DATA_DIR
.venv/bin/python -m uvicorn app.asgi:app --host 127.0.0.1 --port 8000 --workers 1 --no-proxy-headers
```

- `--no-proxy-headers` обязателен за туннелем или прокси на loopback. Иначе uvicorn подменяет адрес клиента по `X-Forwarded-For`, и лимиты обходятся. Все клиенты туннеля тогда делят один bucket.
- Запускать из корня проекта. Пути `DATA_DIR` и `RULESET` привязаны к корню проекта, а не к текущему каталогу (проверено из другого CWD в регрессии координатора).
- `--workers 1`: параллельность заданий задаёт `WORKERS` (дочерние процессы), а не uvicorn. Несколько процессов uvicorn не проверялись.
- Веб-статус на `/` (баннер статуса модели и правил).

### 2.4. Smoke-проверка API (curl)

Заголовок `X-API-Key` обязателен. Загрузка: `multipart/form-data`, поле `file`, тип `video/*` или `application/octet-stream`.

```bash
# 1. Жив ли процесс (без ключа)
curl -s http://127.0.0.1:8000/healthz                       # {"ok": true}

# 2. Неверный или отсутствующий ключ
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/api/v1/model   # 401

# 3. Постановка задания
curl -s -H "X-API-Key: $API_KEY" \
     -F "file=@<clip>.mp4;type=video/mp4" \
     http://127.0.0.1:8000/api/v1/analyze
# {"job_id":"<32 hex>","status":"processing"}

# 4. Опрос статуса
curl -s -H "X-API-Key: $API_KEY" http://127.0.0.1:8000/api/v1/jobs/<job_id>
# без валидированных правил: {"job_id":"...","status":"failed","error":"no_validated_rule"}

# 5. Неизвестный job_id
curl -s -H "X-API-Key: $API_KEY" http://127.0.0.1:8000/api/v1/jobs/0123456789abcdef0123456789abcdef
# 404 {"detail":"job not found"}
```

Проверено 2026-10-18 на сервисе с `DATA_DIR` во временном каталоге и синтетическом клипе 5 с (из `tools.make_synthetic`): шаг 2 → 401, шаг 3 → 200 и `processing`, шаг 4 → `failed/no_validated_rule`, шаг 5 → 404. Реальные клипы в этой проверке не использовались.

Ожидаемое время: клиент загружает файл до 60 с, задание выполняется до 230 с от момента постановки (ожидание в очереди входит в бюджет). Сумма 290 с меньше 5 минут.

## 3. Точные ограничения

Значения по умолчанию из `app/config.py` и `app/detector.py`. Переопределяются переменными окружения.

| Параметр | По умолчанию | Поведение |
|---|---|---|
| `MAX_UPLOAD_MB` | 60 | Загрузка больше лимита: 413 (до чтения тела, при `Content-Length`; при потоковой передаче примерно по лимиту + один чанк) |
| `MAX_DURATION_SEC` | 150 | Клип длиннее: `failed/too_long` |
| `JOB_BUDGET_SEC` | 230 | Бюджет задания от постановки, ожидание в очереди входит. Допустимо (0, 300). Задание сверх бюджета: `failed/time_budget_exceeded` |
| `UPLOAD_TIMEOUT_SEC` | 60 | Общее время приёма тела. Проверка при старте: `UPLOAD_TIMEOUT_SEC + JOB_BUDGET_SEC < 300`, иначе сервис не стартует |
| `RECEIVE_TIMEOUT_SEC` | 15 | Пауза между чанками тела больше лимита: 408 |
| `WORKERS` | 2 | Параллельные дочерние процессы заданий |
| `QUEUE_LIMIT` | 20 | Ёмкость очереди сверх `WORKERS`; задание, которое не успеет в бюджет, получает 429 |
| `DETECTOR_THREADS` | 4 | Потоки ONNX Runtime на задание. Два воркера на одной машине мешают друг другу |
| `DETECTOR_MODEL` | `yolox_s` | `yolox_s` / `yolox_tiny` / `yolox_nano`; по умолчанию yolox_s (640 px ввод) |
| `ALLOW_UNVALIDATED_RULES` | не задана | `1` включает неподтверждённые правила. **Только демонстрация.** Не продуктовый вердикт; `/api/v1/model` показывает `allow_unvalidated_rules` |
| `MAX_INFLIGHT_UPLOADS` | 4 | Одновременные загрузки в `POST /api/v1/analyze`; сверх них 429 |
| `RATE_LIMIT_PER_MIN` | 30 | Загрузки в минуту на IP (token bucket); сверх них 429. Счётчик в памяти одного процесса |
| `POLL_LIMIT_PER_MIN` | 600 | Опросы `GET /api/v1/jobs/*` в минуту на IP; сверх них 429. Проверка до ключа |
| `BIND_JOBS_TO_KEY` | 1 | Задание привязано к хешу ключа в памяти; не durable. `0` отключает |
| `REQUIRE_EMPTY_DATA_DIR` | не задана | `1`: сервис не стартует, если `DATA_DIR` непуст. Файлы не удаляются никогда |
| `TRUST_PROXY` | не задана | `1` доверяет первому `X-Forwarded-For`. По умолчанию заголовки игнорируются |
| `SYNTHETIC_DETECTOR` | не задана | Синтетический детектор только для тестов. `app/asgi.py` отказывает в старте при его наличии без `ALLOW_SYNTHETIC_DETECTOR=1` (проверено: код возврата 1) |

**Частота кадров и разрешение.** Код не требует конкретного fps или разрешения. Шаг выборки вычисляется из fps источника (`SAMPLE_FPS` = 4 кадра/с на этапе 1). Кадры масштабируются до 640 px по ширине (`stage1_width`). Этап 2 берёт 8 кадров/с (`stage2_fps`) только внутри окон кандидатов. Проверено на синтетике 1080p и на наборе 464×848. Другие кодеки (например, перемотка `.mov` h264) не тестировались.

**Что ещё важно:**
- `ONNX_MODEL` (внешняя модель) проверяется по SHA-256 только для известных имён.
- `DETECTOR_PROVIDERS` по умолчанию `CPUExecutionProvider`. CoreML опционален и не измерен сквозным путём.
- Коды ошибок закрытые (`ALLOWED_ERROR_CODES`): пайплайн (`model_missing`, `corrupt_video`, `too_long`, `too_few_frames`, `no_validated_rule`, `too_few_detections`, `zone_unreliable` и др.) и очередь (`time_budget_exceeded`, `worker_crashed`, `invalid_result`, `service_shutting_down` и др.).
- Публичный ответ содержит только `job_id`, `status`, `verdict`, `violations` (и `error` при ошибке). Наблюдения и метаданные наружу не отдаются.

### 4.4. Честный итог этапа 7

- **Установлено:** единственный предрегистрированный прогон выполнен по протоколу (`ab2c71c974fa9d7d`, 17/17, без пропусков). Обе семьи дают измеренный NO-GO. Клипный уровень не лучше «всё положительно» и «только длительность». Локализация не лучше позиционного приора. Холдаут не открывался.
- **Правдоподобно:** в признаках SigLIP2 есть различие внутри клипа, связанное с меткой и присутствующее только в размеченных клипах, причина неизвестна. Нарезка клипов, выбор конечной точки аннотатором и смена сцены вне нарушения не исключены. Идентичность клипа вносит заметную долю дисперсии эмбеддингов.
- **Неизвестно:** существует ли какой-либо визуальный признак нарушения; можно ли визуально проверить метки (4 из 5 не видны на аудите); качество на любых независимых данных.

### Какие данные нужны для будущей работы

Всё перечисленное собирается и хранится локально, по тем же правилам приватности: только агрегаты, без имён, путей, меток и кадров в документах и API.

1. **Позитивные клипы с подтверждённым человеком интервалом START/END**: ориентир около 8–12 клипов. Событие видно, разметка уверенная. Порог гейта P ≥ 4 — минимум, а не цель.
2. **Сопоставимые нормальные контроли**: не меньше 3 подтверждённых уверенных контролей. Предпочтительно в том же клипе, что и позитив, но понимая, что это спаренные, а не независимые единицы. Лучше добавить внешние контроли из других клипов.
3. **Явная семантика меток**: что отмечает время, начало события (onset) или его конец (end), и в каких единицах.
4. **Новый ЗАКРЫТЫЙ набор оценки**, который не видел ни один этап разработки: ни обучающий набор, ни уже использованный holdout.
5. **Подтверждение роли и зоны по каждому клипу**: кто оператор, кто клиент, где рабочая зона.
6. **Единое описание ракурса камеры** для каждого клипа (высота, наклон, что в кадре). Без этого признаки зоны могут измерять не ту сцену.
